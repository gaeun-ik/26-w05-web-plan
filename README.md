# 26-w05-web-plan

5주차 실습② — **보안회사 원페이지 웹사이트 (Plan 기반 제작)**

방금 인라인으로 만든 것과 **동일한 요구사항**의 보안회사 웹사이트를, 이번엔 GitHub Copilot **Plan 모드**로 계획을 먼저 세운 뒤 **Start Implementation**으로 Agent에게 실행을 넘겨 완성하는 실습입니다.

## 시작하기

1. 이 저장소를 **Fork**
2. Fork한 저장소를 로컬에 **Clone**
3. [`guide.md`](./guide.md)를 따라 순서대로 진행

## 만들 결과물 (지난 실습과 동일)

```
nav (앵커링크: Hero / Services / About / Contact)
 └─ hero (회사 슬로건 + 버튼)
 └─ services (서비스 카드 3개, 각 카드에 "자세히 보기" 링크)
 └─ about (회사 소개)
 └─ contact/footer (연락처)
```

파일 구성: `index.html` / `style.css` / `script.js`

## 오늘 쓰는 방식

```
[Plan] 계획 세우기 (코드 변경 없음)
    ↓ "Start Implementation" 클릭
[Agent] 계획대로 파일 생성·수정 (실행)
```

### 📝 프레임워크 비교 소감 (인라인 vs Plan 상세 분석)

- **인라인(Inline) 방식:** 코드를 작성하는 중 떠오른 아이디어를 바로 반영하고 결과를 확인할 수 있어 첫 화면이나 문구, 색상처럼 범위가 작은 수정은 빠르게 진행할 수 있었습니다. 반면 nav, hero, services, about, contact처럼 여러 섹션과 이동 흐름을 함께 맞춰야 할 때는 사전에 전체 구조와 요구사항을 정리하지 않아 변경이 한 부분에만 반영되거나 중요한 항목을 놓칠 수 있었습니다. 구현하면서 구조를 다시 정리하고 예외 상황을 뒤늦게 확인하게 되어 수정이 반복될 수 있다는 점도 느꼈습니다.
- **Plan 방식:** 구현에 앞서 다섯 개 섹션의 구성과 연결 관계, 파일별 역할, 작업 순서를 먼저 정리하고 계획에 따라 구현하니 전체 요구사항을 기준으로 결과를 확인하기 쉬웠습니다. 덕분에 불필요한 코드 변경을 줄이고 섹션 간 일관성을 유지하면서 누락이나 오작동 가능성을 낮출 수 있었습니다. 다만 계획을 세우는 데 초기 시간이 들고, 계획만으로 완성되는 것은 아니므로 실제 화면과 동작을 확인하며 필요한 부분을 다시 조정해야 했습니다.
- **종합 소감:** 간단한 문구나 스타일을 빠르게 시험할 때는 인라인 방식이 편리했고, 여러 섹션과 내비게이션을 함께 구성하는 이번 웹사이트처럼 전체 흐름과 완성도가 중요한 작업에는 Plan 방식이 더 효과적이었습니다. 먼저 Plan으로 범위와 구조를 잡고, 구현 후에는 인라인으로 세부 디자인과 동작을 다듬는 조합이 가장 효율적이라고 느꼈습니다.
